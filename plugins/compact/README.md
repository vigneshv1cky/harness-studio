# @harness-studio/compact

A Claude-like feel for [Harness Studio](../../README.md) in Harness's own colours: denser spacing, serif replies, calmer chrome, plus whole-app zoom.

## What it changes

- **Conversation:** 22px line height (was 24px), 10px paragraph and message gaps (was 16px), tighter code blocks and user bubbles.
- **Composer:** smaller corners and padding, compact send button, smaller stats line. The box keeps Harness's two rows, the text on top (in line with the + button) and the +, access mode menu, model menu and send under it; the usage readings sit centred under the box. The usage line's rules match only the composer's own dock (`[data-composer-dock]`), so Harness's queued-message panel and goal bar stay where Harness puts them.
- **Enter while the agent works reaches it at its next step, as in Claude Code:** Harness calls this Steer; its own default is Queue, which holds the message until the turn ends. On start, the browser half sets Harness's **Settings → General → Send behavior while busy** to Steer when the person has never chosen there (the settings form's user layer has no value), so a later choice of Queue is kept. Cmd/Ctrl+Enter does the other one, so it queues. A steered message that arrives after the agent's last step goes out as the next prompt instead.
- **Queued messages in the chat, like Claude Code desktop's:** messages queued while the agent works (Cmd/Ctrl+Enter, or Enter with Queue chosen) appear at the end of the conversation as your own message bubbles, faded and labelled "Queued", lined up with your other messages; edit, remove and send-now show on hover. Each goes out as a normal prompt, in order, once the agent is free. This restyles Harness's own queue panel (found by its `[data-queue-dock]` attribute): its frame and its "N queued messages" header are hidden, and the list is opened each time the panel appears. A long queued message shows on one line until it is sent.
- **The harness-studio command uses the key saved in the app:** Harness's headless layer turns the saved-key store off for one-off jobs; Compact's `cordis.patch.yml` comes after it in Harness Studio's command-line profile and turns it back on (in the app's profile it is on already). With no saved key, `DEEPSEEK_API_KEY` from the environment or a `.env` file still works.
- **Long turns:** **Settings → Permissions → Long turns** (after Cloud logins for commands) sets how many steps one request may take before the agent asks to continue: 60 (default), 120, 200 or never, saved in `<harness home>/harness-studio/turn-budget.json`. The Host half (`turn-guard.js`) counts steps from the start of each turn, by Harness's own turn and step numbers, so a message you send while the agent works does not restart the count; halfway it adds a note telling the agent to take stock and ask you if it is stuck, and at the limit the next tool call goes through Harness's approval prompt (Allow grants another budget, Reject ends the turn; refused where nothing can ask, as on the command line). Subagents are not paused. It also tells any agent when one tool has returned exactly the same result three and five times in a turn, which Harness's own repeat reminder (identical calls in a row) does not catch.
- **No hover previews in the chat:** the diff preview of a changed-files card and the image preview of an image link stay hidden (clicking still opens the file); the sidebar's own hover cards are unchanged.
- **Right sidebar start page:** compact entry rows instead of large cards.
- **Zoom:** ⌘+ / ⌘− / ⌘0 (Ctrl on Windows/Linux) scale the **whole app**, like Claude's desktop app, in Chrome-style steps from 67% to 200%; the level is remembered. While zoomed, the theme converts every element position, pointer position and window size Harness reads into the zoomed layout's units, so column drags, menus and popovers line up at any zoom; the space beside the macOS window buttons is kept at its real size. This replaces Harness's text-only size shortcut; text size is still adjustable in Settings.

- **Conversation like Claude Code desktop's:** replies at 14px on a 22px line in the chosen chat font, 16px between paragraphs, tables like Claude's (14/20px text, 6×11px cell padding, a rounded 1px border and row lines at 10% of the text colour, a header in the cells' weight on a 5% fill, kept inside the text column with wrapping cells instead of Harness's sideways-scrolling wide tables), code blocks and inline code at 13/19px (Harness draws blocks at 11px), wide tables kept inside the chat area, 12px between transcript items, and one centred 768px column shared by the transcript and the message box, at least 40px from the pane edges.
- **Clearer lines on full pages:** on Plugins, Connectors, Automation tasks, Instructions, About and the Git page, the border colours behind separators and boxes are 8, 16, 20 and 24% of the text colour instead of Harness's 4 to 16%, so rows and sections stand apart; the conversation and dialogs keep Harness's lines. The colours mix from the text colour, so every theme and both schemes follow. Harness's own Plugins and Automation tasks lists sit in rounded, bordered sections with a line between rows, like the Instructions page (Connectors and the Git page do the same in their own plugins).
- **Always allow a website:** the new-site approval card gets a third button, **Always allow for this website**, between Reject and Allow once. Harness's approval has a single grant (allowed once, which the session log records), so the button first saves the site through the Host, which accepts only a site an approval card is asking about right now, and then answers the card with Allow once. Saved sites live in `<harness home>/harness-studio/sites.json` (exact site names, no wildcards, at most 500); calls to them and pages on them pass without asking. **Settings → Permissions → Always-allowed sites** lists them with Remove.
- **Prompt history:** Up in the message box steps back through the prompts sent in this chat (newest first) when the box is empty or the cursor is at its very start; while a recalled prompt is unchanged, Up and Down keep stepping, and Down past the newest brings back your draft. Any edit ends the stepping; the / and @ menus and input-method composing keep their keys. The prompts are read from the chat the box belongs to (its own conversation in a split view: your messages and those sent while the agent worked, no repeats in a row, older turns once loaded), so other chats' prompts never come up and nothing is stored; the list an earlier version kept in this window's storage is deleted on start. A recalled prompt is set through the editor itself, so it sends like a typed one.
- **Colour themes:** **Settings → Appearance → Colour theme**, just below Light or dark, adds Warm (Claude-like ivory and clay), Graphite, Nord, Solarized and High contrast to the default look. Each theme has a light and a dark palette, so Light or dark still picks light, dark or system. A theme's colours go through Harness's own theme service as one override layer on its colour tokens (backgrounds, borders, text, hover and selection fills, accent, links, code and tooltips), and under a theme the left sidebar takes the theme's sidebar colour instead of the default blue-and-violet gradient. The choice is remembered on this computer, and the app starts in it: the theme's colours for the current light or dark choice (both schemes for System) are kept as a boot style that the desktop page adds before its first paint (Harness patch 26), and removed once the theme layer takes over. With the default theme in dark mode the boot style holds Harness's dark page colour, so dark mode does not start white either.
- **Chat font of your choice:** **Settings → Appearance → Chat font**, just below Font size, sets the typeface for messages and replies from presets in four groups — sans-serif (System, the default, plus Helvetica Neue, Avenir Next, Verdana, Gill Sans, Optima, Rounded, Noto Sans, DejaVu Sans), serif (New York, Georgia, Charter, Iowan Old Style, Palatino, Baskerville, Noto Serif), monospace (Fira Code, SF Mono, Menlo, JetBrains Mono, DejaVu Sans Mono) and playful (Comic Sans, Chalkboard, Marker Felt, Trebuchet) — each offered only when installed, or the name of any installed font. Each is drawn with the platform's normal smoothing on a 22px line, and the choice is remembered on this computer. Code keeps its code font.
- **Calmer chrome:** a hairline composer edge and a quieter header line.
- **Narrower left sidebar on demand:** drag its edge down to 230px (Harness stops at 264px), close to Claude Code desktop's width; sessions sit indented under their folder. The word **More** at the foot of the sidebar is centred, with its dots kept at the left, and its menu opens centred over it. The width is remembered; double-click the edge to return to Harness's own width. Column drags cover the window while they run, so crossing the Browser pane's page doesn't swallow them.
- **Claude Code desktop's sizes at 100%** (measured from its window): 13px for the conversation title and message-box controls; 14px on a 20px line for replies, your messages and the message box. The left sidebar uses Claude's 13px text with 12px session times on slightly tighter 26px rows, so more sessions fit beside the Instructions and About rows.
- **Long messages fold:** a message you sent that runs past about ten lines shows its start with a fade and **Show more** at the start of its time-and-copy row (always shown, in the time's grey); **Show less** folds it again, as in Claude Code desktop.
- **Left sidebar top, like Claude Code desktop:** a **Search** field sits where the New Session button was and searches session names as you type (Enter opens the first match, Esc clears, ⌘K jumps to it); **New Session** becomes a row like **Plugins** and **Automation tasks**. The field drives the Workspaces header's own search, which stays hidden.
- **Right sidebar, like Claude Code desktop's side panes:** a slim header with a hairline under it; borderless 26px tabs, the active one in a soft fill, close buttons on hover; the start page as a plain menu instead of bordered cards.
- **Side panes as cards:** each right-sidebar pane is a rounded, bordered card on the sidebar fill, like Claude Code desktop; the browser pane gets a roomier navigation row and a bordered address field.
- **One control per pane:** the conversation header's pane icons open and close panes (the Preview plugin stacks up to two, top and bottom), so each pane header shows only its own title, a fullscreen button and a × that closes it — no tab strip, no new-tab button, no side-by-side split, no second collapse button. The browser pane is the exception: its tabs and + stay, like Claude's browser.
- **No layout motion:** opening or closing a sidebar happens in one step; the centre column no longer eases sideways and the right panes no longer slide in.
- **Panels and popups that stand apart, like Claude Code desktop:** Harness draws menus 58% (light) and 45% (dark) opaque with almost no shadow, so the page shows through them. Menus, lists and dialogs are now solid in both themes (white in light, the raised surface colour in dark) with Claude's popover shadow (24px blur at 12% plus 6px at 8%; stronger in dark mode), and the side panes and message box are white with Claude's panel shadow.
- **About page:** an **About** row under **Settings** at the foot of the sidebar opens a page explaining every Harness Studio feature: what it does, how it works and why, with a list of what is not there yet. Beside the text (when the page is at least 860px wide inside its margins) an "On this page" index lists every section with its number badge and expands only the section being read, with a line marking the current feature; narrower windows get the same index as one "Jump to" menu.
- **Settings search:** a search field at the top of the Settings page list (⌘F or Ctrl+F while Settings is open) lists matching rows from every page as row and page; choosing one opens the page, scrolls to the row and highlights it, and Escape clears the search. Harness renders only the open page, so the index starts from a list of every page's rows and adds the titles and descriptions a page shows each time it is opened, kept in the window's storage.
- **Network for commands:** **Settings → Permissions → Network for commands**, after Permission, chooses On, Off or Only allowed sites (with an editable list) for commands the agent runs. The Host half of this plugin (`index.js`) saves the choice in `<harness home>/harness-studio/network.json`, which the sandbox policy reads before each command (desktop patch 16); the setting has no effect without that patch.
- **Design board, apps, dashboards and charts skills:** the host half registers four skills with Harness's skill registry, so only their names and descriptions reach every request and the body loads when the agent picks one. **design-board** (`skills/design-board.md`) has the agent read the project's real design values, then write `designs/<topic>.board.html`: one `<template data-shared>` of tokens and one `<template data-screen>` per screen or variant, followed by the board runtime (`skills/board-runtime.html`, inserted into the skill body at registration). The runtime turns each screen into iframes of exact widths (375, 768 and 1440 by default, or the screen's `data-widths`), so media queries see a real phone, tablet or desktop; it fits the widest row to the window, pans on scroll or drag, and zooms with Ctrl or ⌘ and scroll. The agent checks the board once in the Browser pane and does not fall back to another browser. **native-apps** (`skills/native-apps.md`) tells the agent where each app toolchain must keep its files inside the sandbox (Swift packages, Xcode, Gradle and Android, npm and Electron, Rust), how to run and check a Mac app through computer use, an Android app in a headless emulator and an iPhone app in the simulator, and what the computer cannot do. **dashboards** (`skills/dashboards.md`) has the agent build `dashboards/<name>/`: a self-contained page that starts with the dashboard runtime (`skills/dashboard-runtime.html`, inserted into the skill body at registration: it receives data from the Dashboards pane or a saved snapshot, asks the pane to refresh, and draws line and bar charts, headline numbers and tables in light and dark), and one refresh script per source in `refresh/` that prints JSON, using the person's own logins or a key in a git-ignored `.env`, never a secret written into a file. **charts-and-diagrams** (`skills/charts-and-diagrams.md`) chooses native charts in decks and workbooks, SVG for standalone charts, icons and diagrams, and Pillow only when a bitmap is required, since the bundled office converter cannot read SVG and there is no plotting library.
- **Cloud logins for commands:** **Settings → Permissions → Cloud logins for commands**, after Network for commands, has a switch each for Google Cloud (`gcloud`, `gsutil`, `bq`), AWS (`aws`), Azure (`az`), Kubernetes (`kubectl`, `helm`), Snowflake (`snow`, `snowsql`), Databricks (`databricks`), PostgreSQL (`psql`, `pg_dump`, `pg_dumpall`, `pg_restore`) and MySQL (`mysql`, `mysqldump`, `mysqladmin`), all off by default; a login none of whose files exist shows "not signed in". The Host half (`cloud-logins.js`) saves the choice in `<harness home>/harness-studio/cloud-logins.json`, which Harness's sandbox policy reads before each command: a switched-on login's files (`~/.config/gcloud`, `~/.aws`, `~/.azure`, `~/.kube`; Snowflake's `~/.snowflake`, or its configuration folder under `~/Library/Application Support` or `~/.config`; `~/.databrickscfg` and `~/.databricks`; `~/.pgpass` and `~/.pg_service.conf`; `~/.my.cnf` and `~/.mylogin.cnf`) leave the sandbox's hidden list, and those that are folders become writable to commands, so the CLI runs as you and refreshes its tokens (a login kept in one file is only readable), and the agent is told which logins it has. The first command in a session that uses a switched-on login asks through Harness's approval prompt (a `tools/pre-execute` listener); allowing it lets that login's later commands in the session run without asking, each login on its own. Commands are recognised by the CLI at the start of a command (after `;`, `&&`, `|`, `(` or `$(`, behind `sudo`, `env` or a variable assignment); a program that starts a CLI another way is not asked about but still has only the switched-on logins. A command run with full access asks through Harness's own escalation prompt instead. The agent's file tools still cannot read the login files.
- **Settings pages:** Harness's fork splits Settings into General, Appearance and Permissions; this plugin puts Colour theme and Chat font on Appearance, its four command and site rows on Permissions, and adds **Computer use** (after Permissions) and **Data** (last) as pages of their own. Its rows use their own classes with the values of Harness's settings rows (16px rows, a hairline divider, 14px titles and 12px notes), so they look the same on pages that have no Harness row; the divider under a page's last row is dropped as on Harness's pages.
- **Asking before new sites:** web fetch (`web_fetch`), Browser pane pages the agent opens (`browser_open`) and pages it opens in your Chrome (the Chrome connector's `chrome_open`) ask before reaching a site for the first time in a session, through Harness's approval prompt; rejecting it stops the request before anything is sent. Sites on this computer pass, and so do the sites on the Network for commands list while it is set to Only allowed sites (matched as the command proxy matches them). A site allowed once is reached without asking for the rest of that session while the app runs; full access lifts the check. The Host half (`site-approval.js`) does this with a `tools/pre-execute` listener that lets other listeners decide first, and a `tools/execute` listener that remembers a site once its call runs; the two are tied by the call itself (Harness passes the same object to both), not by its id, which providers reuse. A call whose address is not text (a list, say) is refused, since the tools would turn it into text unchecked. Pages can move to another site by themselves (a redirect, a script, a clicked link, a local page included), so the plugin also offers its check as a service (`harnessStudioSiteApproval`), and the Browser pane checks the address each step ended up on, leaving a site not approved in the session; the request to that site has been made by then. The setting file is saved one write at a time through a uniquely named temporary file, so concurrent saves cannot leave a broken file. It needs no Harness patch, so it also works in your own Harness; the command-line tool, which does not load this plugin, does not ask. Tests: `node --test plugins/compact/test/*.test.mjs`.
- **ffmpeg on first use:** when the agent needs ffmpeg and neither `ffmpeg` nor `ffprobe` is on the command search path, it calls `ffmpeg_install`, and the host half (`ffmpeg.js`) asks once per session on Harness's question card whether to download a pinned build: FFmpeg 9.0.2 release builds from Martin Riedl's build server (`ffmpeg.martin-riedl.de`, GPL, built with [his Apache-2.0 build script](https://git.martin-riedl.de/ffmpeg/build-script)), ffmpeg and ffprobe as two zips per platform, 56.7 MB on Apple-silicon Macs, 67.5 MB on Intel Macs, 57.4 MB on Linux arm64 and 66.5 MB on Linux x64 (glibc); there is none for Windows. `curl` downloads them through Harness's command runner, sandboxed like the agent's commands and under the session's network setting, into a temporary folder that is the only one it may write; the host checks each zip's size and SHA-256 against the values pinned in `ffmpeg.js`, a second sandboxed command unpacks them and runs `ffmpeg -version`, and only then is the folder renamed to `<harness home>/harness-studio/ffmpeg/9.0.2/`, with the build line and licence recorded in its `.ready` file. Unpacked, the two programs take about 130 MB on an Apple-silicon Mac (Settings → Data shows 126.4 MB, counted in binary megabytes). That folder is appended to the app's `PATH`, so every command the agent runs finds `ffmpeg`, and an ffmpeg you installed yourself still comes first and is used without asking. **Settings → Data** lists it; delete the folder and the next use asks again.
- **Transcription for the agent:** `transcribe` (`transcribe.js`) turns the speech in an audio or video file, or in a part of it, into text with the time range each piece was said in. It accepts the Files tab's marking reference as it stands ("[clip.mp4, 1:10.4 to 1:25.0]") or a separate range, and a language: Chinese, English, Cantonese, Japanese, Korean or automatic. ffmpeg decodes the file or range to raw 16 kHz mono samples in a temporary folder, sandboxed with no network; the samples are read back about 30 seconds at a time, each piece ending at the quietest 100 ms of its last five seconds so a cut rarely splits a word, wrapped as WAV, and sent one at a time to Harness's local speech service from the Voice Input bundle (SenseVoice small on the CPU, with no time stamps of its own). Nothing leaves the computer, and memory stays at one piece plus the recognizer's worker, which Harness stops when idle. Before the first use the agent asks you, on a card, whether Harness may download the recognizer's model (about 241 MB from Hugging Face, pinned by Harness with sizes and hashes); a whole file is limited to 3 hours per call. If you switch Voice Input off on the Plugins page, the tool says so instead.
- **Replies like Claude Code's, in your own instructions:** on the first start the Host half writes Harness Studio's default reply style (`default-agents.md`) as your global instruction file, `<harness home>/AGENTS.md`, which the Instructions tab lists as "Global, all projects": lead with the answer, keep length to the request, use lists, tables and headings only when the content has that shape, link files with workspace-relative paths, give a one-line note before a batch of tool calls, work in few steps (independent reads and commands together, one read per region, no re-read after a successful edit), and finish with what changed and how it was checked, saying plainly what failed or was not verified. It is written once, only when you have no such file (`default-instructions.js` leaves a marker in `<harness home>/harness-studio/`), so a file you already have is kept and one you edit or delete is never rewritten. Harness's own system prompt says nothing about tone or format, so nothing conflicts.
- **Sidebar scrollbar:** a visible grey thumb in both themes while the pointer is over the sidebar.
- **Colours:** Harness's own palette and blue accent, untouched, in both themes.

## Install

Desktop: **Plugins → Add plugin** → the folder `plugins/compact` or a packed `.tgz` → **Install → Enable now**.
Web / CLI: `dsh plugin --profile web add ./harness-studio-compact-0.2.0.tgz`.

Turn it off on its Plugins page to get the stock look back.

## Compatibility

Harness styles use generated CSS-module class names (`gBsEha_panelRow`). The theme matches the stable part after the underscore (`panelRow`), so it survives rebuilds of the same version, but a Harness release that renames components can stop some rules from applying. Tested with `0.2.1-alpha.3`.
